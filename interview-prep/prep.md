## STAR 구조 뼈대

### 1. 통계 자동화 — "문제를 구조로 해결하는 사람"

- **S**: 모델하우스 오픈 첫날, 상담 150건을 실시간으로 처리해야 하는 상황. 수기로는 물리적으로 불가능한 양.
- **T**: 데이터의 관문 역할로서 정확성과 속도 둘 다 책임져야 했음.
- **A**: 첫날 전부 틀어진 걸 확인하고, 원인이 사람이 아니라 구조라고 판단. 다음 날 바로 단일진실공급원 기반 통계 함수 + 오류 가시화 설정 적용.
- **R**: 이후 같은 유형의 오류가 반복되지 않았고, 이 구조가 기본 틀이 됨.

### 2. 엑셀 하위호환성 — "사용자 관점에서 생각하는 사람"

- **S**: 만든 엑셀 파일을 다른 직원들이 열면 함수가 깨지는 문제 발생.
- **T**: 모든 사용자가 문제없이 쓸 수 있도록 개선.
- **A**: 엑셀 버전 차이(2019)가 원인임을 확인. 모든 함수를 하위호환 가능한 것으로 교체하고 각 셀의 용도를 명시.
- **R**: 버전 무관하게 누구나 사용 가능해짐. 인수인계 시 혼란 감소.

### 3. 커뮤니케이션 개선 — "실수에서 시스템을 만드는 사람"

- **S**: 시간 압박으로 상세내역 없이 파일을 먼저 업로드. 내 작업 방식을 모르는 직원이 불완전한 데이터로 보고할 뻔함.
- **T**: 같은 문제가 반복되지 않도록 전파 체계를 만들어야 했음.
- **A**: 업로드 시 특이사항을 반드시 함께 전파하거나 파일명에 상태를 명시하는 규칙을 자체적으로 만듦.
- **R**: 정보 비대칭으로 인한 오보고 리스크가 사라짐.

### 4. 잡일 → 사무직 전환 — "태도로 기회를 만드는 사람"

- **S**: 모델하우스에서 단순 잡일 알바로 시작. 사무직은 교체가 어려운 자리라 자리가 안 남.
- **T**: 사무직으로 전환하고 싶었음.
- **A**: 땜빵 기회마다 적극적으로 들어가 좋은 모습을 보여드리고, 관리자에게 희망을 직접 말씀드림.
- **R**: 다른 현장 사무직 자리를 소개받아 현재까지 신뢰받으며 근무 중.

## 부족한 역량 7가지 (자기 인지용)

### 1. 협업에서 부딪힌 경험
- 도구/프로세스는 있음 (노션, GitHub, 칸반, PR 리뷰, 주1회 회의)
- 보완: 문법 데이터 포함 여부 논의 사례가 있음 (내 의견 기각, 실제 사용자 의견으로 결정)
- 면접에서 더 구체적인 마찰 사례를 정리해둘 필요 있음

### 2. 완성·배포 경험 없음
- hada는 미완성, 모델하우스는 개발 프로젝트가 아님
- 보완: hada 서버리스 버전을 실제 배포하면 해결

### 3. 테스트 경험 없음
- MSW 도입 시도했으나 Next.js 호환 버그로 실패, 모킹 없이 진행 (후회 중)
- 백엔드 협업 시 내 바운더리에서 최대한 테스트 후 이슈 전달
- 보완: 서버리스 버전에 테스트 붙이기

### 4. 성능 판단에 근거 부족
- "조인이 비싸서"의 실측 데이터 없음
- 보완: 프로파일링/벤치마크 경험을 쌓을 것

### 5. 접근성(a11y) 언급 없음
- M3 가이드라인 준수했다면서 접근성 이야기가 없음
- 보완: 접근성 기본 개념 학습 및 적용 경험 만들기

### 6. 기술 깊이 증명 부족
- React Query, 서비스 레이어 분리 등 "했다" 수준. "왜 그 구조를 선택했는지" 설명 필요
- 보완: 기존 코드의 아키텍처 선택 이유를 정리해둘 것

### 7. 정량적 결과 없음
- "시간 안에 처리했다"는 있지만 얼마나 빨라졌는지 수치 없음
- 보완: 가능한 부분은 사후라도 수치화해볼 것

## 예상 질문 & 답변 전략

### "팀에서 갈등이 있었을 때 어떻게 해결했나요?"
→ 문법 데이터 포함 여부 논의. 근거를 제시해서 비교하고, 결론이 안 나면 시간을 두고 다시 토론. 최종적으로 실제 한국어 학습자에게 물어봐서 결정. 내 의견이 기각됐지만 사용자 의견 기반 결정이라 납득함.

### "본인의 장점은?"
→ "어떤 일이든 개선할 점을 찾으려고 합니다." (모델하우스 자동화, 엑셀 하위호환, 커뮤니케이션 규칙 등 사례로 뒷받침)
→ 주의: "의미 없는 일은 못 합니다"라고 말하지 말 것. 같은 내용이지만 프레이밍이 부정적임.

### "해결 방법이 본인이 수행할 수 없는 상황이면?"
→ 내가 할 수 있는 범위에서 최대한 정리하고, 근거를 붙여서 할 수 있는 사람에게 전달함.
→ 사례: ERP 예외 상황에서 과거 유사 사례를 찾아서 처리 방안을 제안, 그대로 적용됨.

### "꼼꼼한 편인가요?"
→ 수입인지 사례. 출근했을 때 책상에 수입인지가 있길래 계약자가 왔다 갔다는 걸 추론, 퇴근 후 상담카드가 나온 게 있는지 확인해서 전일 누계에 반영. 누가 시킨 게 아니라 업무 흐름을 이해하고 있었기 때문에 감지.

### "프로젝트 하면서 아쉬웠던 점?"
→ Anki와 비슷한 앱을 만들면서 Anki 오픈소스를 참고하지 않았음. 선행 사례를 먼저 분석했으면 시행착오를 줄일 수 있었음. 다만 날짜 경계 처리는 나중에 조사해보니 Anki도 즉시 적용 방식이라 커뮤니티에서 문제가 보고되고 있었고, 내가 선택한 "다음 날부터 적용"이 더 방어적인 설계였음.

### "테스트 어떻게 했나요?"
→ 솔직히 부족함. MSW로 API 모킹을 도입하려 했으나 Next.js 호환 버그로 실패. 모킹 없이 진행한 부분은 후회. 백엔드 협업 시 결과가 잘못 나올 때 내 바운더리에서 최대한 테스트하고 이슈를 전달함. 다음 프로젝트에서는 테스트를 먼저 잡겠음.

### "네트워크 공부는 왜?"
→ AI 시대에 대체되기 어려운 영역이 뭘까 고민하다가 인프라·네트워크에 관심을 갖게 됐고, 정보통신기사 필기 합격 후 실기 응시 완료 (결과 2026.05.09 발표).
→ 전산직 지원 시: 사내 인프라 관리, 장애 대응에 직접 활용 가능한 지식.

### "전산직에서 어떻게 기여하겠나?"
→ "전산직이 대체되기 쉽다"고 말하지 말 것.
→ 대신: "IT 업무가 클라우드와 자동화로 빠르게 변하고 있지만, 실제 장비를 운영하고 현장에서 장애에 대응하는 영역은 사람이 직접 판단하고 움직여야 하는 일이라고 생각합니다. 이 영역에서 전문성을 쌓아 회사에 기여하고 싶습니다."

## 전산직 지원 시 강점 포인트

- 모델하우스에서 ERP 운영, 엑셀 자동화, 데이터 관리를 실무로 해봤음
- 사용자 환경이 다양한 상황(엑셀 버전 차이)에서 호환성 문제를 직접 해결한 경험
- 소통 구조 문제를 인식하고 규칙을 만들어 개선한 경험
- 정보통신기사 실기 응시 완료 (결과 2026.05.09 발표)
- 프론트엔드 개발 경험(TypeScript, React, Next.js)이 전산직에서 사내 시스템 개선에 활용 가능

## 프론트엔드 지원 시 강점 포인트

- hada 프로젝트에서 기획, API 설계, 프론트엔드 전체 담당
- 결정적 셔플 설계: 진도 유실, prefetch 불가, 서버 의존 등 별개로 보이던 문제들의 근본 원인이 "비결정적 순서"라는 점을 발견하고 해결
- M3 가이드라인 준수, 5가지 윈도우 사이즈 클래스 디자인 (회고: 2~3개가 현실적)
- 엣지케이스 발견 및 대응 경험 (날짜 경계, 시간여행, 멀티탭)
- Anki 대비 더 방어적인 날짜 경계 설계
- 사용자 관점: "Anki가 좋은데 친구들이 못 쓴다"에서 출발, 엑셀 하위호환성도 같은 맥락

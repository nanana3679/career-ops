# 부족 역량 보충 계획

interview-prep.md에서 파악한 7가지 부족 역량을 이 프로젝트의 어디에서 보충할 것인지.

## 1. 협업에서 부딪힌 경험 → 보충 불가 (개인 프로젝트)

개인 프로젝트로는 직접 보충 불가. 대신 **설계 결정 과정을 면접에서 설명 가능하도록 기록**한다.

- 모든 트레이드오프를 interview-cards.md에 Q&A로 축적
- "혼자 했지만, 이런 선택지가 있었고 이런 근거로 결정했다"를 말할 수 있는 상태
- 비평 에이전트 리뷰 → 피드백 반영 과정 자체가 "다른 시각을 수용하는 태도" 증거

## 2. 완성·배포 경험 없음 → Step 1에서 즉시 해결

| 시점 | 행동 | 면접 답변 |
|------|------|-----------|
| Step 1 | Vercel에 배포 + claude.ai 커넥터 연결 | "실제로 배포하고, 외부 서비스(claude.ai)에서 연동까지 확인했다" |
| Step 4 | MCP 도구 + 웹앱 전체가 프로덕션에서 동작 | "개인 프로젝트지만 실사용 가능한 상태로 배포했다" |

hada의 실패("거의 완성했지만 배포 못 함")를 반복하지 않기 위해, **Step 1부터 배포 상태를 유지**한다.

## 3. 테스트 경험 없음 → Step 2-3에서 보충

hada에서 MSW 도입 실패 후 테스트 없이 진행한 것을 후회했음. 이번에는:

| 대상 | 테스트 종류 | 도구 | 시점 |
|------|------------|------|------|
| `shuffle.ts` (결정적 셔플) | 단위 테스트 | Vitest | Step 3 |
| `fsrs.ts` (스케줄링 래퍼) | 단위 테스트 | Vitest | Step 3 |
| `validators.ts` (Zod 스키마) | 단위 테스트 | Vitest | Step 2 |
| 카드 CRUD API | 통합 테스트 | Vitest + Supabase local | Step 2 |
| 학습 세션 큐 로직 | 단위 테스트 | Vitest | Step 3 |

**원칙**: 핵심 로직(셔플, FSRS, 큐 관리)에만 테스트 집중. UI 테스트는 MVP에서 제외.

면접 답변: "hada에서 테스트 부재를 후회했고, 이번에는 핵심 알고리즘에 단위 테스트를 먼저 작성했다. 특히 결정적 셔플은 같은 seed에 같은 결과가 나오는지 테스트가 필수였다."

## 4. 성능 판단에 근거 부족 → Step 2-3에서 실측

hada에서 "조인이 비싸서"라고 했지만 실측 없었음. 이번에는 판단에 수치를 붙인다.

| 측정 대상 | 방법 | 시점 |
|----------|------|------|
| tsvector 전문 검색 응답 시간 | Supabase query explain + API 응답 시간 로깅 | Step 2 |
| 결정적 셔플 성능 (1000장 기준) | console.time / Vitest bench | Step 3 |
| 학습 세션 초기 로딩 시간 | Next.js Server Timing / Vercel Analytics | Step 3 |
| ts-fsrs 스케줄링 계산 시간 | 벤치마크 (카드 1장 당) | Step 3 |

면접 답변: "이전 프로젝트에서 감으로 성능 판단한 것을 반성하고, 이번에는 실측으로 확인했다. 예를 들어 tsvector 검색은 카드 N장 기준 Xms가 나왔고, LIKE 검색 대비 Y배 빨랐다."

## 5. 접근성(a11y) 언급 없음 → Step 3 학습 UI에서 보충

학습 UI가 접근성을 적용하기 가장 좋은 대상. 카드 넘기기가 핵심 인터랙션이므로:

| 적용 항목 | 구현 | 시점 |
|----------|------|------|
| 키보드 네비게이션 | Space=정답확인, 1/2/3/4=평가 단축키 | Step 3 |
| ARIA 라벨 | 카드 상태, 진행률을 스크린리더에 전달 | Step 3 |
| 색상 대비 | Tailwind 기본 팔레트 + 대비 검증 | Step 3 |
| Lighthouse 접근성 점수 | 90점 이상 목표, 실측 기록 | Step 3 완료 시 |

면접 답변: "hada에서 M3 가이드라인을 따르면서도 접근성을 놓친 것을 인지했다. 이번에는 학습 UI에 키보드 단축키와 ARIA를 적용하고, Lighthouse 접근성 점수 N점을 달성했다."

## 6. 기술 깊이 증명 부족 → 전 과정에서 interview-cards.md로 해결

CLAUDE.md의 "면접 Q&A 기록" 규칙이 이 역량을 직접 보충한다.

**기록 예시 (예상):**

| 기능 | 면접 질문 | 깊이 |
|------|----------|------|
| 결정적 셔플 | "왜 Math.random 대신 seed 기반 셔플인가?" | 알고리즘 선택 근거 |
| tsvector | "LIKE vs tsvector 차이는? 한국어 검색은?" | DB 인덱싱 원리 |
| FSRS 래퍼 | "ts-fsrs의 반환값을 어떻게 DB에 매핑했나?" | 라이브러리 통합 설계 |
| Auth.js v5 | "v4 대신 v5를 선택한 이유는? App Router 통합에서 뭐가 달랐나?" | 프레임워크 이해도 |
| MCP API key | "해시 저장을 선택한 이유는? bcrypt가 아니라 SHA-256인 이유는?" | 보안 설계 |
| 카테고리 vs 덱 | "왜 계층적 덱 대신 평탄한 태그를 선택했나?" | 데이터 모델링 |

## 7. 정량적 결과 없음 → 배포 후 측정 가능한 수치 확보

| 지표 | 측정 방법 | 시점 |
|------|----------|------|
| Lighthouse 점수 (성능/접근성/SEO) | Chrome DevTools | Step 3 완료 |
| 번들 사이즈 | `next build` 출력 | 매 Step 완료 |
| API 응답 시간 (p50/p95) | Vercel Analytics 또는 수동 측정 | Step 2-4 |
| 검색 응답 시간 (카드 N장) | Supabase explain analyze | Step 2 |
| 학습 세션 로딩 시간 | 브라우저 Performance API | Step 3 |

면접 답변: "배포 후 Lighthouse 성능 N점, 접근성 N점. 검색 API는 카드 1000장 기준 p95 Xms. 이전 프로젝트에서 정량적 근거 없이 판단한 것을 반성하고, 이번에는 수치를 기록했다."

# 포트폴리오 계획

---

## 1. hada-reboot — 서버리스 버전 재구축

### 배경

hada는 기술적으로 거의 완성했지만 배포하지 못했다. 원인:
- Spring Boot + Redis는 이 앱 스케일에 불필요한 오버엔지니어링
- AWS 서버 비용 문제와 팀원 이탈로 유지 불가
- 결정적 셔플 설계 덕분에 서버가 학습 상태를 유지할 필요가 없으므로 서버리스 전환 가능

### 목표

hada 프로젝트를 포크하여 Spring Boot 백엔드를 제거하고, Supabase 기반 서버리스로 재구축하여 실제 배포까지 완료한다.

### 기술스택 변경

| 영역 | 기존 (hada) | 변경 (hada-reboot) |
|------|------------|-------------------|
| 백엔드 | Spring Boot + Redis | Supabase (PostgreSQL) + Next.js API Routes |
| 인증 | 커스텀 JWT | Auth.js v5 (Google/GitHub OAuth) |
| SRS 알고리즘 | 백엔드 구현 | ts-fsrs (프론트에서 직접 계산) |
| 배포 | AWS (미배포) | Vercel |
| 스타일링 | SCSS + M3 | Tailwind CSS |

### 핵심 작업

1. **Spring 의존성 제거**: 백엔드 API 호출을 Supabase 직접 쿼리로 교체
2. **인증 교체**: 커스텀 JWT → Auth.js v5. OAuth로 가입 허들 제거
3. **SRS 로직 클라이언트 이전**: ts-fsrs로 스케줄링 계산을 프론트에서 수행. 결정적 셔플 덕분에 서버가 순서를 관리할 필요 없음
4. **데이터 모델 재설계**: 정규화 문제 회고 반영 — 카드 상세정보를 비정규화하여 조인과 prefetch 불필요하게 설계
5. **날짜 경계 처리**: 설정 변경을 다음 날부터 적용하는 방식 유지 (Anki보다 방어적인 설계)
6. **Vercel 배포**: Step 1부터 배포 상태 유지. hada의 실패("거의 완성했지만 배포 못 함")를 반복하지 않음

### 면접에서 말할 수 있는 것

- "이전 프로젝트의 오버엔지니어링을 인지하고, 동일한 기능을 서버리스로 재구축했다"
- "정규화 판단 오류를 회고하고 비정규화 설계로 개선했다"
- "결정적 셔플 설계가 서버리스 전환을 가능하게 한 근거"
- "실제 배포까지 완료하여 이전 프로젝트의 미완성 문제를 해결했다"

## 2. Wordle Decks — AI 컨텐츠 부트스트래핑 + 재홍보

### 배경

첫 번째 배포에서 실패한 원인:
1. **콜드 스타트**: 초기 컨텐츠가 본인 덱뿐이라 사용자 유입 동기가 없었음
2. **튜토리얼 부재**: Wordle을 모르는 사람의 진입 장벽을 해소하지 못함

발견한 기회: 텍스트 기반 컨텐츠(단어 목록)라는 특성상 AI로 덱을 대량 생성할 수 있음

### 목표

AI 에이전트로 다양한 주제의 덱을 대량 생성하여 콜드 스타트를 해결하고, 타겟 커뮤니티에 홍보하여 실사용자를 확보한다.

### Phase 1: AI 컨텐츠 생성

#### 에이전트 설계

- **입력**: 주제 (예: "포켓몬 1세대", "LOL 챔피언", "수능 영단어", "일본 애니 캐릭터")
- **출력**: Wordle 덱 형식에 맞는 5글자 단어 목록 + 덱 제목 + 설명
- **제약**: 5글자 단어만 허용, 중복 제거, 너무 어렵거나 비속어 필터링

#### 덱 카테고리 전략

| 카테고리 | 예시 | 타겟 커뮤니티 |
|----------|------|-------------|
| 게임 IP | 포켓몬, LOL, 발로란트, 원신 | 게임 커뮤니티, 디시, 레딧 |
| 애니/만화 | 원피스, 나루토, 귀멸의 칼날 | 애니 커뮤니티 |
| 교육 | 수능 영단어, TOEIC, 한국사 | 수험생 커뮤니티, 에브리타임 |
| 트렌드 | K-POP 그룹명, 드라마 캐릭터 | 팬덤 커뮤니티 |
| 일반 | 동물, 음식, 나라, 직업 | 범용 |

#### 생성 목표

- 최소 50개 덱 (카테고리당 10개)
- 사람이 올린 것처럼 자연스러운 제목/설명
- 덱별 5~20개 단어

### Phase 2: 튜토리얼 추가

- 첫 방문 시 인터랙티브 튜토리얼 표시
- Wordle 규칙 + 이 플랫폼의 사용법을 3단계로 설명
- "건너뛰기" 가능, 한 번 완료하면 다시 안 뜸

### Phase 3: 타겟 커뮤니티 홍보

#### 전략

불특정 다수 홍보가 아닌, 특정 IP의 팬 커뮤니티에 해당 IP 덱 링크를 직접 공유

#### 실행

1. 게임/애니 IP 덱을 만들고 해당 커뮤니티에 "이거 만들어봤는데 해보세요" 식으로 공유
2. 카카오톡 공유 시 ISR 기반 OG 미리보기가 작동하므로 링크만 던져도 덱 정보가 보임
3. 반응이 좋은 IP를 파악하고 해당 카테고리 덱을 추가 생성

#### 측정 지표

| 지표 | 측정 방법 | 목표 |
|------|----------|------|
| DAU | Vercel Analytics | 일 10명 이상 |
| 덱 플레이 수 | DB 집계 | 일 50회 이상 |
| 사용자 생성 덱 수 | DB 집계 | 주 5개 이상 (AI가 아닌 사용자) |
| 공유 클릭 수 | 이벤트 로깅 | 추적 |

### 면접에서 말할 수 있는 것

- "콜드 스타트 문제를 직접 경험하고, AI 컨텐츠 생성으로 해결 전략을 실행했다"
- "텍스트 기반 UGC 플랫폼의 특성을 활용하여 AI 부트스트래핑이 가능하다는 점을 발견했다"
- "불특정 다수 홍보에서 커뮤니티 타겟 홍보로 전환한 이유와 결과"
- "DAU, 플레이 수 등 정량적 지표로 결과를 추적했다"

## 포트폴리오 제출 구성

| 프로젝트 | 어필 포인트 | 배포 상태 |
|----------|-----------|----------|
| **hada-reboot** | 설계 역량 (결정적 셔플, 서버리스 전환 근거, 회고 반영) | Vercel 배포 완료 |
| **Wordle Decks** | 플랫폼 운영 (콜드 스타트 해결, AI 활용, 사용자 확보 전략) | Vercel 배포 완료, 실사용자 존재 |
| **not4k** | 도메인 전문성 기반 설계 (입력난→인식난 분산) | (선택) |
